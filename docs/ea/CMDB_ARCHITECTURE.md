# EA CMDB Architecture

**Enterprise Architecture Configuration Management Database**

This document describes the optimized, lean architecture for managing EA data as a single source of truth (CMDB).

---

## Overview

The CMDB maintains a clean data flow:

```
INPUT           PROCESSING          CMDB (SOURCE OF TRUTH)    OUTPUT
ea_inputs/ ──→ ea_discovery ──→ archi_inputs/* ──→ presentation ──→ ea_diagrams/
                                                        generator
```

---

## Three Directories Only

### 1. INPUT: `ea_inputs/` (User-Maintained)

Raw system descriptions and specifications. Users update this with new systems, changes, and view requirements.

**Structure:**
```
ea_inputs/
├── 01_company_context/          # Organizational information
│   ├── company_overview.txt
│   └── business_capabilities.txt
├── 02_IT_systems/               # System descriptions (organized by domain)
│   ├── Commercial/
│   │   ├── crm_systems.txt
│   │   └── sales_apps.txt
│   ├── Operations/
│   │   ├── erp_systems.txt
│   │   └── supply_chain.txt
│   └── ...
├── 03_global_standards/         # Enterprise policies
│   ├── MSS.md
│   ├── security_standards.txt
│   └── cloud_strategy.txt
└── views/                       # Diagram specifications (YAML)
    ├── operations_app_landscape.yaml
    ├── commercial_asis_crm_current.yaml
    └── commercial_app_matrix.yaml
```

**Ownership:** User maintains. Add systems, update descriptions, create view specs.

**Format:** Markdown, CSV, Excel, plain text. Any human-readable format.

---

### 2. CMDB: `archi_inputs/` (Auto-Generated, Read-Only)

Canonical enterprise architecture model in ArchiMate format. This is the system of record.

**Structure:**
```
archi_inputs/
├── elements.csv                 # All EA elements
│   - ID, Type, Name, Documentation
│   - Types: ApplicationComponent, DataObject, Capability, etc.
├── relations.csv                # All relationships
│   - ID, Type, Source, Target, Documentation
│   - Types: Serving, Flow, Composition, Access, etc.
├── properties.csv               # Element properties
│   - ID, Key, Value
│   - Keys: Domain, Region, Lifecycle Status, Criticality, etc.
├── model.xml                    # ArchiMate Model Exchange (open in Archi tool)
├── views.csv                    # View metadata
├── property_schema.yaml         # Property definitions
└── (other metadata files)
```

**Ownership:** Generated by `ea_discover_directory()` and `ea_generate_archi()`. Never manually edit.

**How it's generated:**
1. `ea_discover_directory()` processes all files in `ea_inputs/`
2. Claude extracts EA objects (applications, capabilities, relationships)
3. `ea_generate_archi()` converts to ArchiMate CSV/XML format
4. Result is written to `archi_inputs/`

**To update the CMDB:**
- Edit files in `ea_inputs/`
- Run `ea_discover_directory()` to regenerate
- CMDB is automatically updated

---

### 3. OUTPUT: `ea_diagrams/` (Auto-Generated Deliverables)

Presentation-ready diagrams for slides and reports.

**Structure:**
```
ea_diagrams/
├── operations_app_landscape.drawio
├── commercial_asis_crm_current.drawio
├── commercial_app_matrix.drawio
└── (other diagrams)
```

**Ownership:** Generated by `ea_generate_presentation_diagram()`. User refines in draw.io.

**How it's generated:**
1. Reads a YAML view spec from `ea_inputs/views/`
2. Loads element selection rules from the spec
3. Intelligently curates elements (hubs + strategic focus)
4. Generates clean draw.io XML
5. Writes to `ea_diagrams/*.drawio`

**To use:**
1. Generate: `ea_generate_presentation_diagram("ea_inputs/views/my_view.yaml")`
2. Open: https://app.diagrams.net → File → Open → select `.drawio` file
3. Refine: Move elements, adjust colors, add annotations (optional)
4. Export: Download as PNG or PDF for slides

## Workflow

### Adding a New System

**Step 1: Update Input**
```
Edit ea_inputs/02_IT_systems/Commercial/crm_systems.txt
Add: "Salesforce CRM integrates with Tableau for reporting"
```

**Step 2: Regenerate CMDB**
```
ea_discover_directory("ea_inputs")
→ Processes all files, discovers new apps/relationships
→ Updates archi_inputs/* with new elements
```

**Step 3: Check Result**
```
ea_get_data_summary()
→ Shows updated element counts
→ Verify new system is in the model
```

### Creating a New Diagram

**Step 1: Create View Spec**
```yaml
# ea_inputs/views/my_diagram.yaml
view:
  name: "My Architecture"
  documentation: "Shows systems in Operations domain"

elements:
  include:
    - where:
        type: "ApplicationComponent"
        Domain: "Operations"

relationships:
  include:
    - type: ["Serving", "Flow"]
      between: "included_elements"

grouping:
  by_property: "Sub-Domain"
  order: ["Manufacturing", "Distribution", "Finance"]

layout:
  algorithm: "grid"
  columns: 3
  spacing_x: 100
  spacing_y: 50
```

**Step 2: Generate Diagram**
```
ea_generate_presentation_diagram("ea_inputs/views/my_diagram.yaml")
→ Generates ea_diagrams/my_diagram.drawio
```

**Step 3: Refine in draw.io**
```
1. Open https://app.diagrams.net
2. File → Open → ea_diagrams/my_diagram.drawio
3. Adjust positions, colors, labels as needed
4. Export to PNG/PDF
```

## MCP Tools

### Input Processing
- **`ea_discover(text)`** - Extract EA objects from text description
- **`ea_discover_directory(path)`** - Batch process all files in directory

### CMDB Management
- **`ea_generate_archi()`** - Generate ArchiMate CSV/XML files
- **`ea_get_data_summary()`** - Get CMDB statistics and overview

### Output Generation
- **`ea_generate_presentation_diagram(spec_path)`** - Generate slide-ready diagram
- **`ea_generate_mermaid(type)`** - Generate technical documentation diagrams

### View Specs
- **`ea_list_view_specs()`** - List all YAML view specifications
- **`ea_list_available_elements(type)`** - List elements for view design
- **`ea_generate_views_from_specs()`** - Generate views.csv from YAML specs

## Best Practices

### For ea_inputs/ (User Input)

1. **Keep it organized** - Use the 3-level structure (01_, 02_, 03_)
2. **Write descriptions, not specs** - Natural language is fine, let discovery extract structure
3. **Update incrementally** - Add new systems as they're documented
4. **Use YAML for views** - View specs are code, keep them in `views/` subdirectory

### For archi_inputs/ (CMDB)

1. **Never manually edit** - Always regenerate from `ea_inputs/`
2. **Commit to git** - It's the source of truth after discovery
3. **Don't delete files** - Delete from `ea_inputs/` instead, then regenerate
4. **Check after changes** - Run `ea_get_data_summary()` to verify

### For ea_diagrams/ (Output)

1. **Use draw.io for refinement** - Generated diagrams are baselines
2. **Keep specs close** - Relate diagrams back to YAML specs in `ea_inputs/views/`
3. **Version in git** - Store final `.drawio` files for team collaboration
4. **Export for distribution** - Use draw.io to export PNG/PDF for slides

---

## Cleanup Rules

- **Delete:** Legacy files, intermediate artifacts, old reports
- **Keep:** `ea_inputs/`, `archi_inputs/`, `ea_diagrams/`
- **Archive:** Long-term session notes if needed, but don't clutter `/ea_outputs`

---

## Architecture Benefits

| Aspect | Benefit |
|--------|---------|
| **Clarity** | 3 directories = clear input/process/output |
| **Maintainability** | CMDB is auto-generated, not hand-curated |
| **Extensibility** | Add new systems by editing text files |
| **Auditability** | All changes trace back to `ea_inputs/` |
| **Scalability** | Supports 1000+ applications in single model |
| **Presentation** | Output directly to slides via draw.io |
