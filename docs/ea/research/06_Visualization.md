EA Visualization in Power BI

Visualizing the enterprise architecture (EA) landscape is critical for communication and analysis. Using tools like Microsoft Fabric and Power BI, architects can turn their EA data (from sources like Neo4j graph or YAML DSL files) into insightful visuals. Below are strategies for representing an EA graph (nodes and relationships), capability matrices, and key metrics in Power BI, using the purchase order automation scenario as an example:

Graph Visualization with Deneb (Vega/Vega-Lite): Power BI doesn’t have a native interactive graph network visual, but we can leverage Deneb, a custom visual that allows writing Vega/Vega-Lite specifications. With Deneb, one can create a force-directed graph showing EA nodes (e.g. applications, processes, capabilities) as circles and their relationships as lines. For instance, you could visualize the Purchase Order process node connected to an “ERP System” application node and a “Procure-to-Pay” capability node, indicating relationships between them. Community examples (like Davide Bacci’s force-directed Vega spec) provide a good starting point
evaluationcontext.github.io
. In practice, you would prepare a dataset of nodes and links (e.g. a table with Source, Target, and Relationship type). The Vega spec can use a force simulation to position nodes and draw links. Tip: You might use different colors or symbols for different entity types (blue for processes, green for systems, etc.), and tooltips to show node details on hover. Using Deneb’s capabilities, such a graph can be made interactive (for example, filter the data model by a selected capability to highlight connected components). One PBI developer noted that the out-of-the-box Force-Directed custom visual was insufficient, and switching to a Deneb/Vega solution allowed full control to achieve the desired network graph
evaluationcontext.github.io
. Thus, Deneb is the recommended approach for rich EA diagrams in Power BI when you need to visualize relationships like which applications support the Purchase Order process and how that ties into business capabilities.

Capability Maturity × Criticality Matrix: Beyond graphs, a useful analytic visualization is a matrix or scatter plot mapping each business capability’s importance vs. maturity. On one axis (e.g. X) plot the capability’s current maturity level, and on the other axis (Y) its strategic importance or criticality. This highlights high-criticality but low-maturity capabilities as prime candidates for investment. For example, if Procurement Management capability is extremely critical to the business (high Y-axis) but its maturity (perhaps measured via people/process/technology ratings) is low, it would appear in the bottom-right quadrant – a red flag indicating modernization like PO automation is urgent. Industry practice defines Strategic Importance as “how relevant or critical a capability is to business success” and Capability Maturity as “how well the organization performs that capability today (across people, process, information, and technology)”
bizzdesign.com
. Using a scatter chart visual in Power BI, each capability can be a bubble (perhaps size representing number of applications or cost). You can add quadrant lines or use conditional formatting: e.g. color bubbles by whether maturity is below target. In our example, Purchase Order Processing might be a sub-capability of Procurement; if it’s manually done (low maturity) but very important for finance controls (high importance), it would be clearly indicated as a pain point on this chart. This matrix helps execs and architects quickly grasp which areas (capabilities) need attention. The same concept can be extended as a heatmap or a matrix visual with conditional color: rows = capability, columns = maturity level attained (or target gap), with cell color intensity showing criticality. The key is linking data: you might maintain a table of capabilities with columns for “CriticalityScore” and “MaturityScore” (both on 1-5 scale from your assessments) and feed that into such a visual. The scatter plot is easy to implement in Power BI and gives a powerful 2x2 view aligning with methods like business capability assessment frameworks
bizzdesign.com
.

KPI Cards and Summary Metrics: An EA dashboard should also surface key metrics in easy-to-read cards or KPI visuals. For modernization, examples of KPIs could be: % of applications on-prem vs. cloud, # of manual processes remaining, Average capability maturity score, or Value delivered (e.g. hours saved by automation this quarter). In Power BI, Card visuals or KPI visuals can display a single number with context (variance or trend). For instance, after implementing PO automation, a KPI card might show “PO Cycle Time: 1.2 days” vs a previous value of 5 days, indicating improvement. Another card could show “Legacy Systems Decommissioned: 10/50” to track progress of an overall program. To create these, you will define DAX measures in the dataset. For example, a measure AvgCapabilityMaturity := AVERAGE(Capability[MaturityScore]) can feed a card showing the enterprise’s average maturity level. Or a measure PO_CycleTime := AVERAGEX(PO_Transactions, DATEDIFF([RequestDate],[ApprovalDate],DAY)) to compute actual performance from data, shown as a KPI with a target. Formatting should be consistent: use data labels, units, and color signals (RAG status) to make the KPIs intuitive. On a Fabric/Power BI report for EA, you might position a row of such cards at the top (e.g. “Total Applications”, “% Standardized Tech Stack”, “Processes Automated”), giving executives a quick health summary.

Data Modeling: Lakehouse/Warehouse Tables from Neo4j or DSL YAML: A critical step is feeding the above visuals with a robust dataset. EA data often lives in a graph database (Neo4j) or in YAML files (if using infrastructure-as-code or model-as-code approaches). To use this in Power BI, transform it into tabular format. There are a few approaches:

Using the Neo4j BI Connector: Neo4j offers a BI connector that exposes Cypher queries as relational tables accessible via ODBC/JDBC
neo4j.com
. For example, you can write a Cypher query to return all nodes and their properties of a certain type (e.g. all Applications with their attributes) and all relationships of interest (e.g. (:Application)-[:SUPPORTS]->(:Capability)). The BI connector lets Power BI retrieve these results as if querying a SQL view. This is convenient for scheduled refresh. If using Microsoft Fabric’s Warehouse, you could also pull data from Neo4j into a staging SQL table. Alternatively, one can query the Neo4j REST API directly in Power BI (using M scripts in Power Query) – though this requires some custom work since Neo4j’s REST is POST-based and returns nested JSON
medium.com
. In any case, the goal is to flatten the graph: for instance, create a table of Applications, a table of Capabilities, a table of Processes, and bridge tables for their relationships (like an App-to-Capability mapping table). This yields a star schema in Power BI where these entities are dimensions that can be sliced and counted.

From DSL (YAML) to Lakehouse: If EA artifacts are defined in YAML (for example, an architecture model coded in a DSL), you can parse these files and load into a Fabric Lakehouse (Delta tables). Using an Azure Function or Fabric Notebook, one could convert YAML into tabular data. For instance, a YAML might list capabilities and their attributes, and another section lists applications and links to capabilities. A script can parse that into CSVs for capabilities, applications, and their link table. Once in the Lakehouse, Power BI can directly use the tables via DirectLake or import mode. This approach is tool-agnostic – it doesn’t rely on having the actual Neo4j runtime, just the exported DSL data.

Modeling Guidance: Maintain surrogate keys for each entity (capability_id, app_id, etc.) to manage relationships. Use consistent naming and possibly type columns if you combine different entities in one table. For example, one might have a single Nodes table (with all objects) and a Relationships table (with columns for SourceID, TargetID, RelType). In Power BI, you might not create formal relationships between these if using a network visual (since the Vega spec will handle it), but for other visuals (like counting how many applications per capability), you’ll want relationships. In that case, having separate dimension tables and a fact-like table such as ApplicationCapability (with AppID, CapID) works well. If using star schema, the “fact table” could be something like an Architecture Assessment Fact (each record is a capability supported by an application, including perhaps a maturity score or criticality). This allows slicing counts of applications by capability or vice versa easily, and writing DAX measures like “# of Apps in Procurement domain” or “Average maturity of capabilities supported by a particular system.”

DAX Measures and Visual Design: With the data model in place, define measures for any computed metrics (as mentioned with KPIs). Also utilize hierarchies if applicable – for example, capabilities might have a hierarchy (Capability Group > Capability). In our PO example, Purchase Order Processing could be under a higher-level Procurement capability. Power BI allows drilling down visuals if such a hierarchy is set. For visual formatting, align with EA standards: e.g. use the same color coding for domains or layers as your architecture framework (business = blue, application = green, etc.), so the visuals resonate with familiar EA diagrams. Provide interactive elements: filter panes or slicers to filter visuals by domain, by modernization phase, by risk level, etc. One might have a slicer for “Phase (Discover/Deliver/etc.)” to focus the view on systems in a particular phase of the roadmap. Another example is linking a Power BI map visual if relevant (say, if showing data centers or office locations related to apps, though not directly needed for POs).

Linking Visuals to EA Types: Design the report so that clicking on one visual filters others (“edit interactions” in Power BI). For instance, clicking a particular capability on the maturity-criticality scatter could filter a table or list of applications (fact sheets) that support that capability. Selecting the Purchase Order Process node in the force-directed graph could trigger (via cross-filter) a details pane showing that process’s attributes or its related capability and applications. This requires that the underlying data has proper relationships or at least that the visuals share common fields for cross-filtering (Deneb may need measures or manual filtering logic since it's not a native visual, but it can respond to filters if the data is properly fed). Using Power BI Drillthrough pages is also effective: e.g. you can right-click on an Application name and drillthrough to a page that shows the full System Fact Sheet information (pulled from the dataset) or a diagram of that single application’s interfaces.

In summary, representing EA data in Power BI involves modeling the data from graph or YAML into tables and then using a combination of advanced visuals (Deneb for graphs, custom charts for matrices) and standard visuals (scatter plots, cards, tables) to convey different views. For the purchase order automation scenario, the final Power BI dashboard might include: a network graph highlighting the PO process and its link to systems (perhaps showing the legacy vs target system in different colors), a matrix scatter showing that procurement capabilities are lagging in maturity vs their importance, a set of KPI cards tracking automation benefits (e.g. “PO Automation Coverage: 80% of orders auto-approved”), and maybe a table listing applications with columns like “Retire/Replace/Renovate decision” and phase. By thoughtfully combining these, stakeholders from executives to engineers can interact with the EA model – seeing the “big picture” via graphs and matrices, and also drilling into specifics with tabular data and fact sheets – all updated from the single source of truth (Neo4j or YAML) through the Fabric pipeline. This ensures traceability (every visual is backed by data points from the EA repository) and provides a living architecture view that stays current as the modernization progresses.
